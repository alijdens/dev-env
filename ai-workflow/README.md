# ai-workflow

Centralized, tool-agnostic instructions for AI coding assistants (Claude Code, Codex, ...). Edit once here, `git pull` on any machine, and every configured tool picks up the change.

## Layout

- `AGENTS.md` — the general instructions/preferences file, installed as each tool's global config file. References `docs/` files through the `{{AI_WORKFLOW_DOCS_DIR}}` placeholder (see below) instead of a hardcoded path, since this repo isn't guaranteed to be cloned to the same location on every machine.
- `docs/` — supporting docs that `AGENTS.md` loads conditionally (e.g. `pull-requests.md`, `planning.md`). Drop new files here and reference them from `AGENTS.md`; they become available to every installed tool automatically, no re-install needed.
- `skills/` — agent skills, loaded on demand, all prefixed `sdd-` (spec-driven development) so they are easy to tell apart from other installed skills: `sdd-setup-task-workflow` (project setup, project docs), `sdd-planning` (feature design), `sdd-claim-task` (claiming and implementing tasks), `sdd-review-task` (reviewing a task's PR), `sdd-answer-questions` (working through open questions) and `sdd-orchestrate` (running tasks end to end with sub-agents). They hold only triggers and skill-specific instructions and point to `docs/task-workflow/` for the shared ones.
- `plugins/claude-code/` — Claude Code plugins that hook into its interface rather than the model: `sdd-decisions` draws a band above the prompt with the open questions and the decision holding up the most work (see its [README](plugins/claude-code/README.md)). `plugins/claude-code/install.sh` links them into `~/.claude/skills/`; the top-level installer offers that step for Claude Code.
- `bin/` — commands the docs and skills reference by name (e.g. `pull-pr-description`, `sdd` for the task workflow in `docs/task-workflow/`). `install.sh` adds this directory to `PATH` in `~/.zshrc`/`~/.bashrc`.
- `install.sh` — resolves placeholders and symlinks the result, plus `docs/`, into each tool's config directory, puts `bin/` on `PATH`, installs git hooks that re-run it after pulls and checkouts, and for Claude Code asks whether to install the plugins (yes by default; `--no-plugins` skips the question).
- `tests/` — pytest suite for `bin/sdd` (`pytest ai-workflow/tests`, run by the `ai-workflow tests` GitHub Actions workflow). Each test drives the CLI against throwaway git repos and bare remotes.
- `.rendered/` — generated by `install.sh`, gitignored. Holds the resolved copies of `AGENTS.md` and `skills/` that tools are actually symlinked to.

## Installing

```sh
./install.sh            # installs for all supported tools, asks about the Claude Code plugins
./install.sh --no-plugins # same, without the plugins question
./install.sh claude      # installs only for Claude Code
./install.sh codex        # installs only for Codex
./install.sh agents       # installs only for generic .agents
```

This creates:

| Tool             | Symlinked to                                           |
|------------------|--------------------------------------------------------|
| Claude Code      | `~/.claude/CLAUDE.md`, `~/.claude/docs`, `~/.claude/skills/<skill>`, `~/.claude/skills/<plugin>` (if accepted) |
| Codex            | `~/.codex/AGENTS.md`, `~/.codex/docs`, `~/.codex/skills/<skill>`    |
| Agents (generic) | `~/.agents/AGENTS.md`, `~/.agents/docs`, `~/.agents/skills/<skill>` |

Re-running is safe: existing correct symlinks are left alone, and any pre-existing real file/dir is backed up (`*.bak.<timestamp>`) before being replaced. Skills are linked one by one, so skills installed from elsewhere stay in the same `skills/` dir; links to skills removed from this repo are cleaned up.

### The `{{AI_WORKFLOW_DOCS_DIR}}` placeholder

`AGENTS.md` and `skills/` never hardcode an absolute path to `docs/`, since this repo can be cloned anywhere. Instead they use the literal placeholder `{{AI_WORKFLOW_DOCS_DIR}}`. `install.sh` never edits the tracked files in place (that would conflict with `git pull`); instead it renders copies into `.rendered/` with the placeholder substituted for this checkout's actual `docs/` path, and symlinks tools to those rendered copies. If you ever see the literal `{{AI_WORKFLOW_DOCS_DIR}}` text in a tool's loaded instructions, it means files got linked in directly instead of through `install.sh` — re-run `install.sh`.

After editing `AGENTS.md` or files in `skills/`, re-run `install.sh` to refresh the rendered copies (docs added to `docs/` itself need no re-run, since that directory is symlinked live). Pulls and checkouts do this automatically through the `post-merge`, `post-checkout` and `post-rewrite` hooks, which run `install.sh --refresh` for the tools already installed; existing hooks that aren't ours are left alone.

Cursor is intentionally not included — it has no global instructions file, only per-project `AGENTS.md`/`.cursor/rules` or UI-managed User Rules.

## Task workflow

An opt-in, per-project workflow for features too big for one PR. Agents record the design as architecture decision records (ADRs) and split the work into tasks with dependencies, all kept as files, so the reasoning behind the code stays reviewable and several people or agents can work on tasks in parallel without duplicating effort.

It needs `python3` (3.9+) and, for shared mode, `gh` logged in to the repo's GitHub host; `graphviz` (`dot`) is optional, for rendering the dependency graph.

You drive it by asking your agent; the installed skills and the `sdd` CLI do the rest:

1. **Set up** a repo once: "set up the task workflow". Pick a mode:
   - **Shared**, for repos you own or collaborate on: the data lives in the repo (or a separate one), and `AGENTS.md` gets a section telling agents about it.
   - **Local**, for repos you don't own: the data lives only on your machine and nothing about the workflow reaches the repo, its commits or its PRs. Agents don't see it until you ask for one of the steps below.

   The agent then offers to write two short project docs, `goal.md` (the problem, the users, what success looks like, non-goals) and `principles.md` (the rules every change must respect), through a section-by-section interview that keeps them in scope and within a length limit. Both are optional and can be written or revised later ("write the project goal", "the goal changed"); planning and reviews read them so no feature is designed in isolation.
2. **Plan** a feature: `/sdd-planning` or "plan feature X". The agent first builds a reading list of what the feature builds on (`sdd context`: the foundation ADRs, the ADRs and specs in the feature's areas, the tasks that used them and the questions on them) and confirms it with you, then designs the feature and writes ADRs, specs and tasks. ADRs are immutable once accepted (a changed decision is a new ADR that amends or supersedes the old one); specs describe how things are and are updated by the PRs that change them. Either can end with a short `## Review checks` list, the project-specific things a reviewer verifies on changes in its areas; `sdd checks` collects them per area or task, so a bugfix in one area gets a few checks and a feature across three gets the union, with nothing global beyond `principles.md`. In shared mode this goes to main through a PR before any task starts.
3. **Work** on a task: "work on task X" (or "what tasks are ready?"). The agent claims it, branches and implements, and stops before committing. In shared mode the claim is a PR, so each task has exactly one owner; merge it to let the agent continue.
4. **Finish**: "create a PR for task X" commits the work and opens the PR. When the task data lives in the code repo, merging that PR also marks the task done; with a separate data repo or in local mode, `sdd done X` runs after the merge instead.
5. **Review**: "review the PR for task X". The agent checks the PR against its task and ADRs: scope, unplanned breaking changes, task/ADR references, the task's state after merging, whether the tests actually test the feature, and redundant tests. It reports findings and the PR's risk level without changing anything.
6. **Orchestrate** (optional): the agent runs ready tasks end to end with worker agents: each claims and implements a task, a reviewer agent reviews the PR, the worker applies the feedback, and the orchestrator approves the PR (when GitHub allows it) and merges it if its risk is within the merge policy. Claim PRs are always merged. It stops when nothing can progress and reports where each task ended up. Invoke it as `/sdd-orchestrate [concurrency] [merge=none|low|medium|high|all] [slug...]` (defaults: 1 worker, `merge=none`, all ready tasks), or the same in words:

   ```text
   /sdd-orchestrate                                  # 1 worker, leave every PR for you to merge
   /sdd-orchestrate 3 merge=low                      # 3 workers, merge low-risk PRs
   /sdd-orchestrate 2 merge=all add-rate-limit-store add-rate-limit-middleware
   orchestrate the tasks with 3 workers, merging up to medium risk
   ```

Follow-ups and shortcuts found along the way become tech-debt tasks. Open questions become files too (`sdd ask`): each links the tasks and ADRs it concerns and must carry enough context to be answered without the conversation that raised it, and a question that blocks a task keeps it out of `sdd ready` until you answer it. `/sdd-answer-questions` walks you through them one at a time, most blocking first: a few lines on where each came up and why it matters, more on request, then your answer is recorded and turned into tasks or ADRs where it calls for them (`sdd questions` lists them, `sdd blockers` only those that are the only thing holding up a task, with the work waiting behind it, `sdd answer <slug>` closes one). `sdd --help` lists the commands for checking state yourself (`sdd ready`, `sdd list`, `sdd show <slug>`, `sdd brief <slug>` for a task with everything linked to it, `sdd --main ...` to read main instead of your checkout). The agent-facing details are in `docs/task-workflow/`; `docs/task-workflow/lessons.md` records the cases that shaped its checks, for whoever changes them next.

## Content policy

Everything under this directory must stay generic and shareable: no personal information, company/employer names or specifics, internal tool or system names, credentials, tokens, or any other private context. Treat it as if it could be published publicly. When adding or editing a doc here, keep it scrubbed of anything that only makes sense in one particular company/team/project — that kind of context belongs in a repo-level doc instead, which these files already say takes precedence when it conflicts.
