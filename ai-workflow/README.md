# ai-workflow

Centralized, tool-agnostic instructions for AI coding assistants (Claude Code, Codex, ...). Edit once here, `git pull` on any machine, and every configured tool picks up the change.

## Layout

- `AGENTS.md` — the general instructions/preferences file, installed as each tool's global config file. References `docs/` files through the `{{AI_WORKFLOW_DOCS_DIR}}` placeholder (see below) instead of a hardcoded path, since this repo isn't guaranteed to be cloned to the same location on every machine.
- `docs/` — supporting docs that `AGENTS.md` loads conditionally (e.g. `pull-requests.md`, `planning.md`). Drop new files here and reference them from `AGENTS.md`; they become available to every installed tool automatically, no re-install needed.
- `plugins/claude-code/` — Claude Code plugins that hook into its interface rather than the model: `pending-items` draws a band above the prompt with the decisions and approvals the model is still waiting on from you (see its [README](plugins/claude-code/README.md)). `plugins/claude-code/install.sh` links them into `~/.claude/skills/`; the top-level installer offers that step for Claude Code.
- `bin/` — commands the docs reference by name (e.g. `pull-pr-description`). `install.sh` adds this directory to `PATH` in `~/.zshrc`/`~/.bashrc`.
- `install.sh` — resolves placeholders and symlinks the result, plus `docs/`, into each tool's config directory, puts `bin/` on `PATH`, installs git hooks that re-run it after pulls and checkouts, and for Claude Code asks whether to install the plugins (yes by default; `--no-plugins` skips the question).
- `.rendered/` — generated by `install.sh`, gitignored. Holds the resolved copy of `AGENTS.md` that tools are actually symlinked to.

## Installing

```sh
./install.sh            # installs for all supported tools, asks about the Claude Code plugins
./install.sh --no-plugins # same, without the plugins question
./install.sh claude      # installs only for Claude Code
./install.sh codex        # installs only for Codex
./install.sh agents       # installs only for generic .agents
```

This creates:

| Tool             | Symlinked to                                           |
|------------------|--------------------------------------------------------|
| Claude Code      | `~/.claude/CLAUDE.md`, `~/.claude/docs`, `~/.claude/skills/<plugin>` (if accepted) |
| Codex            | `~/.codex/AGENTS.md`, `~/.codex/docs`    |
| Agents (generic) | `~/.agents/AGENTS.md`, `~/.agents/docs` |

Re-running is safe: existing correct symlinks are left alone, and any pre-existing real file/dir is backed up (`*.bak.<timestamp>`) before being replaced.

### The `{{AI_WORKFLOW_DOCS_DIR}}` placeholder

`AGENTS.md` never hardcodes an absolute path to `docs/`, since this repo can be cloned anywhere. Instead it uses the literal placeholder `{{AI_WORKFLOW_DOCS_DIR}}`. `install.sh` never edits the tracked `AGENTS.md` in place (that would conflict with `git pull`); instead it renders a copy into `.rendered/AGENTS.md` with the placeholder substituted for this checkout's actual `docs/` path, and symlinks tools to that rendered copy. If you ever see the literal `{{AI_WORKFLOW_DOCS_DIR}}` text in a tool's loaded instructions, it means `AGENTS.md` got linked in directly instead of through `install.sh` — re-run `install.sh`.

After editing `AGENTS.md`, re-run `install.sh` to refresh the rendered copy (docs added to `docs/` itself need no re-run, since that directory is symlinked live). Pulls and checkouts do this automatically through the `post-merge`, `post-checkout` and `post-rewrite` hooks, which run `install.sh --refresh` for the tools already installed; existing hooks that aren't ours are left alone.

Cursor is intentionally not included — it has no global instructions file, only per-project `AGENTS.md`/`.cursor/rules` or UI-managed User Rules.

## Content policy

Everything under this directory must stay generic and shareable: no personal information, company/employer names or specifics, internal tool or system names, credentials, tokens, or any other private context. Treat it as if it could be published publicly. When adding or editing a doc here, keep it scrubbed of anything that only makes sense in one particular company/team/project — that kind of context belongs in a repo-level doc instead, which these files already say takes precedence when it conflicts.
