# Task Workflow: Working on a Task

The claim exists to prevent duplicated effort, so it is a prerequisite of working on a task:

- "Work on task X" means claim it (including its claim PR in shared mode), branch, and implement. Stop there: don't commit or open the implementation PR.
- "Create a PR for task X" means all of the above, plus finishing it (step 6).
- "Can you claim task X?" is a question: answer it, take no action.

## Claims in shared mode

`sdd start <slug>` re-checks on the remote main that the task is `todo`/`tech-debt` with all prerequisites done, then opens a claim PR (branch `claim/<slug>`, not a draft) that moves it to `in-progress` and stamps a unique `claimed:` field. It runs in a throwaway worktree, so a dirty checkout doesn't matter. A second claim of the same task fails to push the same branch while the first PR is open; if it gets through anyway, its PR conflicts with main once the first claim merges. So main shows exactly one owner per task.

The claim PR must be merged before implementing. Unless authorized to merge it, give the user the PR link and wait.

## Steps

1. **Pick.** If the user didn't name a task, `sdd ready` lists the ones whose prerequisites are done. It reads your checkout, which may be stale; `sdd start` re-checks against the remote main. A task with something in the `needs` column (a credential, the user's go-ahead) is picked only when the user asks for it and provides what it needs.
2. **Load context.** `sdd brief <slug>` prints the task's state, prerequisites and dependents, then the task file, its ADRs and business rules, each followed by the records that changed it since (its amendments, or its successor once superseded), its specs (the feature spec among them) the questions linked to it (answered questions may settle something the task file predates), the Goal and acceptance criteria of the tasks that depend on this one, and last the review checks of the records and specs it links. ADRs come as their Intent and Decision, without Context, Alternatives considered and Consequences, and answered questions with only their Answer: `--full` adds the rest when that leaves you unsure why. A table of contents with each part's size comes first; a brief too long to print in full goes to a file whose path it prints. A spec the task only uses (`uses:`) comes as its Summary. Read the brief instead of opening those files one by one, and read more of a used spec only when the summary leaves you unsure how to call it; if the task turns out to change that component, link its spec with `sdd link <slug> --spec <spec>` and say so in the PR. The business rules and each ADR's Intent say what is wanted, so they settle the cases nobody planned; the feature spec is the guideline for what the task leaves open; the review checks are what the code keeps from its first line, not only at review. The dependents say what this task must leave room for (what it exports, a variant that takes a transaction, room in a return type, the outcome a response carries: `reviewing.md`, "Dependents can build on it"); building what they deliver is theirs, and a PR that does is out of scope. Read a dependent's Notes (`--full`) only when its criteria leave unclear what it will call. When the Notes don't say what a prerequisite delivered, read that task's file too. Nothing else from the task data: if the task seems to need an ADR or a business rule that isn't linked (code it changes cites one, `sdd context --path` finds them), that's a planning gap; link it with `sdd link <slug> --arch <adr>` or `--rule <rule>` and say so in the PR.
3. **Claim.** `sdd start <slug>`. If it fails or its PR conflicts with main, someone else got the task first: close the PR if there is one, report it, and don't work around it. In local mode it just moves the file. When merging the claim is authorized (an orchestrated run, or the user said so), `sdd start <slug> --merge --branch` also merges the claim PR and does step 4; it refuses if GitHub won't merge yet or the checkout has uncommitted changes.
4. **Branch.** Once the claim is on main, implement in a branch named `<slug>` created from the remote main (`git fetch` first; `--branch` does this and fails rather than branch from a local main it couldn't refresh). If the working copy has uncommitted changes, ask before switching branches. The branch name is the one place the slug appears in local mode too: slugs read as ordinary branch names, and it's how a reviewer finds the task.
5. **Implement** against the task's acceptance criteria.
   - **Code references** tell a reader which record to load for the full reasoning, instead of a long comment block or nothing at all. Add one only where the code's shape follows from a decision a reader would otherwise question, or where it enforces a business rule: a one-line reason plus the record, e.g. `# Limits are per API key, not per user (adr: 2026-10-12-rate-limit-strategy)`, `# At most 3 pictures a day (rule: 2026-10-12-daily-picture-cap)`. A rule is best enforced in one place every path goes through, with a test pinning it; new code that reaches the same data goes through that place rather than checking the rule again. Use `task: <slug>` only for context specific to a task rather than a lasting decision (e.g. a temporary shim until another task lands). Don't tag code just to mark that it changed: blame plus the PR links cover provenance.
   - Build what each criterion says. A criterion that can't be met as written (it contradicts an ADR, a principle, or what a prerequisite delivered) is said so in the PR and recorded as a question that `--blocks` this task; it isn't reinterpreted, and a question doesn't make it met (`reviewing.md`, "Task state").
   - If a decision comes up that passes the test in `planning.md`, "Architecture decisions" (hard to reverse, spans components, constrains later work, real alternatives), add an ADR (`sdd adr`) and list it in the task's `arch:` frontmatter; something the product wants from now on, general enough to answer other questions too, is a business rule (`sdd rule`, in `rules:`). Either lands `proposed`: the PR says so, since merging it doesn't make the decision the user's. Anything smaller is no record: it is the code, a line in the spec where a reader needs it, and the PR description.
   - Out-of-scope follow-ups or shortcuts become `sdd new <slug> --tech-debt --title "..."`. A follow-up that needs designing first (several tasks, a decision to make) is an idea instead: `sdd idea <slug> --title "..." --areas ... --task <this task>`, Idea and Context filled in (see `overview.md`).
   - When the task or its ADRs leave something open, settle it from the business rules, the ADRs' Intent, the feature spec and the conventions in the code when they answer it, and say so in the PR when it was a judgement call. What they don't answer, don't guess silently and don't leave in chat: `sdd ask <slug> --title "..." --task <this task>` and fill in Question and Context (see `overview.md`), including the assumption you went on with. Most such questions are details: record them and go on. Only if you can't proceed without the answer, add `--blocks <this task>`, stop, and tell the user (in an orchestrated run, the orchestrator: it holds the PR, `orchestrating.md`). If it decides how a dependent task must be built, `--blocks` that task instead. The question file rides in the implementation PR. A question is for something only the user can decide; a fix you could just make (a missing link, a typo in a doc) is a tech-debt task or part of the PR, not a question.
   - If the change alters how something described in a spec works, update that spec in the same PR; specs are kept current by the PRs that change them. The review checks in `sdd brief` are what the reviewer will verify in the task's areas. A decision or rule the task can't follow as worded goes through `planning.md`, "Changing a record": when its intent covers the case, follow the intent and say so in the PR. When its wording would have to change, that is the user's call: record a question carrying the restatement you'd propose, and don't work around it with an exception, in the record or in the code. A task's PR doesn't change what an accepted record says.
   - A task is one PR. When it turns out far bigger than the size target in `../pull-requests.md`, split it only along a clear cut: one the feature spec, the task's business rules and ADRs already draw (a component or interface the spec's Shape separates, criteria that touch disjoint parts), where this PR still leaves main working and delivers its share whole. Then, in this PR: create the rest as a new task with `--after <this task>` and the same `--arch`, `--rule` and `--spec` links, move the acceptance criteria it takes over there word for word, add the new task as a prerequisite of each dependent that needs the moved part (`sdd dep add`; dependents are downstream, so this PR may edit them), and say in the PR description where the cut is and what it follows from. Without such a cut, record a question that `--blocks` this task, with the candidate cuts in its Context, and stop: where to split is the user's call. Other re-planning (new dependencies on tasks outside this one's downstream) goes to main first, as planning changes do; tell the user. Don't let the size target push work out of the task without a split either: a PR far over it with no clear cut means the task was planned too big; say so in the PR description, so the next plan splits earlier.
   - If the change alters a port or interface that another todo task is planned to implement, that task's criteria must change too. A task downstream of this one (it lists this task in `after:`, directly or through others) can't be claimed before this PR merges, so its criteria may be edited in this PR. Any other task's edit goes to main first as a small planning PR (`sdd ship`; in an orchestrated run, open it and report it, the orchestrator merges it). The reviewer checks it either way.
   - Notes added to the task file may record what was built, but they don't settle a choice: anything they introduce that the criteria or ADRs don't cover is still a question.
   - A change a user sees (a page, a component, a CLI's output) is exercised in the running app before the PR, started the way the project's docs say; what the task's tests don't reach is where the bugs are. The capture goes in the PR per `../pull-requests.md`.
   - Once the diff is in place, and before running the project's checks, add the review checks of the areas it touches: `sdd checks --area <area>...` with the narrowest areas that fit (`sdd areas` lists them; a top-level one pulls in every check under it). The reviewer adds the same ones whatever the task links, so a check met only after the review costs a fix round. One that applies and comes from a record the task doesn't link is a planning gap: link the record as in step 2, meet the check, and name the link in the PR.
6. **Finish** (only when asked for the PR). Run the project's checks and `sdd validate` (its errors must be fixed; its warnings matter only for files this PR touches), then commit and open the PR following `../pull-requests.md`, with the slug in the title and links to the task file and its ADRs in the description. Name the commit the checks ran on in the report back to whoever asked for the PR (the user or the orchestrator), not in the description, which would need an edit on every push. Before claiming a criterion's guard or bound is tested, prove the test fails without it (`../testing.md`, "Prove a test can fail"). When the task is marked done depends on where the data lives, because dependents become ready the moment it is:
   - Data in the code repo (the usual shared setup): `sdd done <slug>` on the branch before committing, so merging the PR is what marks the task done.
   - Separate data repo or local mode: the task stays `in-progress` until the PR merges. Whoever merges it (the user, or the orchestrator) then runs `sdd done <slug>`, which opens a PR in the data repo, or just moves the file in local mode. Say so in the PR description in the separate-repo case.
7. **Abandon.** `sdd release <slug>` (add `--tech-debt` to park it there) opens a release PR moving it back, so someone else can pick it up.

## Fix rounds

In an orchestrated run, a fix round on an open PR starts at step 5 with the task already claimed, and its findings come as the ID of a review comment on the PR (`reviewing.md`, "In an orchestrated run"):

1. Read it with `gh api repos/{owner}/{repo}/issues/comments/<id> --jq .body`. It holds everything the round needs, so the PR's other comments don't need reading. Its first line, `<!-- sdd-review pr=<number> round=<round> commit=<sha> -->`, must name the PR and round the prompt gave and the branch's head (`git rev-parse HEAD`); if it doesn't, stop and report the mismatch instead of fixing anything.
2. Decide each finding: fix it, or reject it with a reason. Reject one only when what it claims isn't so, when it is out of the task's scope, or when a record or project doc says otherwise, never because the fix costs too much: the re-review judges each reason and re-raises the ones that don't hold. A finding flagged `hold`, or one the orchestrator decided, goes as the prompt says.
3. Fix, run the checks (step 6), commit and push.
4. Post the decisions as one comment, the way the review was posted, whose first line is `<!-- sdd-decisions pr=<number> round=<round> review=<review comment ID> commit=<pushed head> -->`, followed by each finding with what was done or why it was rejected.
5. Report back the commit the checks ran on, the decisions comment's ID, and each rejected finding in one line with its reason. Mark `disputed` a finding you reject again after the re-review re-raised it: the orchestrator decides it.

In local mode, none of the code, commits or PRs mention task slugs, ADRs or the workflow, the branch name aside: skip code references and the slug/links in step 6.
