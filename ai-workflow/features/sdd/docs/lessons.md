# Task Workflow: Lessons

Why the instructions say what they say. Each entry records something that slipped through the workflow, what the instructions checked at the time, and what was added. Add one when you change a check because of a case like these; without the case, the next edit removes the check as noise. Agents running the workflow don't load this file.

Cases are described generically (content policy in the README): the pattern, not the project.

## 2026-10-29: five merged tasks re-reviewed by fresh reviewers

A sample of the largest merged tasks of one project (an authorization engine, login identities, a tenancy migration, invitations, member and grant management) was re-reviewed from scratch. Every PR had already gone through one or two review-and-fix rounds that caught real problems (cycle bounds, legacy data, a notifier channel, a conditional write), so the baseline worked. What it missed clustered in areas `reviewing.md` never asked about. Findings and the checks they led to:

- **A depth limit that didn't bound work.** The engine's check memoized results per node but deleted the entry when a node errored on the depth limit, and the union kept trying siblings, so every path re-evaluated the failed subtree: exponential time once any branch hit the limit. The test named for the bound used a fan-out below the limit, so the error path never ran. The acceptance criterion ("recursion is bounded") was ticked from the test's name. Added: check claimed bounds at and past the boundary and what the error path leaves in cached state (Scope); flag test parameters below the limit under test (Tests).
- **Trust evaluated at the wrong time.** Login identities stored the provider's self-reported verified-email flag and decided at link time whether to trust it from the current configuration. Rows written while the trust flag was off became link targets once an operator turned it on: an account-takeover path through a config change, and the code comment claimed the opposite protection. Nothing in the review asked what a flag flip does to persisted rows. Added: the "Authentication and authorization hold up" section, in particular settings that gate trust and the trust-boundary list; the review rated auth changes `high` but had no auth-specific check to earn it.
- **A criterion contradicted by the code, recorded as a question, task marked done.** A legacy bridge kept looking users up by email against two acceptance criteria. The deviation was honestly recorded as an open question, which the review accepted as enough. Added: a criterion the code contradicts, recorded only as a question, is not met (Task state); a deviation from an ADR needs an ADR, not a question that leaves the code as is (Scope).
- **A failed retry reported as success with stale data.** Resending an invitation whose email delivery failed answered 200 with the previous send's timestamp, and the PR description said it would be null. Only acceptance criteria were checked against the diff, not the description's claims, and nobody read the task that would build the UI on this response. Added: PR description claims are checked like criteria (Scope); responses a dependent acts on carry the outcome it needs (Dependents).
- **A Goal-level guarantee with no artifact.** The task's Goal said accepting an email invitation "also verifies the address"; nothing marked anything verified anywhere. The criteria were all met, so the review passed it. Added: guarantees stated in words in the Goal or an ADR map to an observable artifact (Scope).
- **Shapes the next tasks couldn't use.** Four of five tasks shipped something their dependents will have to rework: a delete with no transaction-taking variant where the dependent must compose it, an authenticator returning a bare principal where scopes will be needed, a grant upsert kept unexported with its tuple projection already copied into a second package. The reviewer was never told to read the dependents. Added: the "Dependents can build on it" section, and the dependents' task files in the reading list.
- **Permission tests that couldn't tell routes apart.** Route tests used an owner (every permission) and a stranger (none); declaring the wrong permission on a route (letting a collaborator delete) would have passed. A 200/403 pair read as coverage. Added: each declared permission needs a denial from a principal holding the neighbouring permissions (Tests).
- **Tokens in every row of a listing.** A share token was in every calendar of the list endpoint, which is what the assistant loads to pick a calendar, against a principle about sending the model only what the operation needs. The reviewer applied the principle to the create path only. Added: data-exposure principles apply to list and read endpoints (Goal and principles).
- **Delete order that only works on a single-writer database.** A delete swept derived tuples before deleting the owning row, which orphans a concurrently written tuple on an MVCC engine; the project's stack decision said not to rely on the single writer. Added: walk statement order against a concurrent insert (Authentication and authorization).
- **Smaller test gaps, each seen more than once:** assertions that only check "some error"; concurrency tests whose goroutines may all take the fast path; invariant tests asserting rows but not tuples; a table-rebuild migration whose test didn't assert the index came back; composition-root wiring that a wrong constant would silently defeat; assumptions recorded in questions with no test pinning them. Added as bullets under Tests.
- **Task-file loopholes.** Three of five PRs added "added during implementation" Notes to their own task that changed observable behavior (status codes, filters, stricter rules) without a question; one task went done with a criterion moved to another task by a planning PR and nothing in the done file saying so; one PR changed a port another todo task implements and that task's plan was fixed only after the merge. Added: Notes don't settle assumptions, moved criteria leave a dated line, changed ports update the implementing task's criteria (Task state, Dependents); the same rule for workers in `working.md`.

## 2026-10-30: an orchestrated run where review rounds cost more than the implementation

Two tasks went through two and three review rounds each. Each round was a fresh reviewer that re-read the whole diff and re-ran the full local check suite, and found a new handful of low findings every time, so the loop kept going on nits. One reviewer, while probing a test, removed the build cache volume every other agent's checks shared, and the next two check runs took minutes instead of seconds. Added: re-reviews get the commit range of the fixes and the decided findings, and review only those (Re-reviews); a round with only low findings ends the loop (`orchestrating.md`); read-only includes shared machine state. Separately, a task that a later decision had invalidated carried the hold only as a Notes line, so `sdd ready` still offered it and a worker was spawned to discover it: holds are blocking questions now (`planning.md`, `answering.md`).
