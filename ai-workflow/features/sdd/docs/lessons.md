# Task Workflow: Lessons

Why the instructions say what they say. Each entry records something that slipped through the workflow, what the instructions checked at the time, and what was added. Add one when you change a check because of a case like these; without the case, the next edit removes the check as noise. Agents running the workflow don't load this file.

Cases are described generically (content policy in the README): the pattern, not the project.

## 2026-10-29: five merged tasks re-reviewed by fresh reviewers

A sample of the largest merged tasks of one project (an authorization engine, login identities, a tenancy migration, invitations, member and grant management) was re-reviewed from scratch. Every PR had already gone through one or two review-and-fix rounds that caught real problems (cycle bounds, legacy data, a notifier channel, a conditional write), so the baseline worked. What it missed clustered in areas `reviewing.md` never asked about. Findings and the checks they led to:

- **A depth limit that didn't bound work.** The engine's check memoized results per node but deleted the entry when a node errored on the depth limit, and the union kept trying siblings, so every path re-evaluated the failed subtree: exponential time once any branch hit the limit. The test named for the bound used a fan-out below the limit, so the error path never ran. The acceptance criterion ("recursion is bounded") was ticked from the test's name. Added: check claimed bounds at and past the boundary and what the error path leaves in cached state (Scope); flag test parameters below the limit under test (Tests).
- **Trust evaluated at the wrong time.** Login identities stored the provider's self-reported verified-email flag and decided at link time whether to trust it from the current configuration. Rows written while the trust flag was off became link targets once an operator turned it on: an account-takeover path through a config change, and the code comment claimed the opposite protection. Nothing in the review asked what a flag flip does to persisted rows. Added: the "Authentication and authorization hold up" section, in particular settings that gate trust and the trust-boundary list; the review rated auth changes `high` but had no auth-specific check to earn it.
- **A criterion contradicted by the code, recorded as a question, task marked done.** A legacy bridge kept looking users up by email against two acceptance criteria. The deviation was honestly recorded as an open question, which the review accepted as enough. Added: a criterion the code contradicts, recorded only as a question, is not met (Task state); a deviation from an ADR needs an ADR, not a question that leaves the code as is (Scope).
- **A failed retry reported as success with stale data.** Resending an invitation whose email delivery failed answered 200 with the previous send's timestamp, and the PR description said it would be null. Only acceptance criteria were checked against the diff, not the description's claims, and nobody read the task that would build the UI on this response. Added: PR description claims are checked like criteria (Scope); responses a dependent acts on carry the outcome it needs (Dependents).
- **A Goal-level guarantee with no artifact.** The task's Goal said accepting an email invitation "also verifies the address"; nothing marked anything verified anywhere. The criteria were all met, so the review passed it. Added: guarantees stated in words in the Goal or an ADR map to an observable artifact (Scope).
- **Shapes the next tasks couldn't use.** Four of five tasks shipped something their dependents will have to rework: a delete with no transaction-taking variant where the dependent must compose it, an authenticator returning a bare principal where scopes will be needed, a grant upsert kept unexported with its tuple projection already copied into a second package. The reviewer was never told to read the dependents. Added: the "Dependents can build on it" section, and the dependents' task files in the reading list.
- **Permission tests that couldn't tell routes apart.** Route tests used an owner (every permission) and a stranger (none); declaring the wrong permission on a route (letting a collaborator delete) would have passed. A 200/403 pair read as coverage. Added: each declared permission needs a denial from a principal holding the neighbouring permissions (Tests).
- **Tokens in every row of a listing.** A share token was in every calendar of the list endpoint, which is what the assistant loads to pick a calendar, against a principle about sending the model only what the operation needs. The reviewer applied the principle to the create path only. Added: data-exposure principles apply to list and read endpoints (Goal and principles).
- **Delete order that only works on a single-writer database.** A delete swept derived tuples before deleting the owning row, which orphans a concurrently written tuple on an MVCC engine; the project's stack decision said not to rely on the single writer. Added: walk statement order against a concurrent insert (Authentication and authorization).
- **Smaller test gaps, each seen more than once:** assertions that only check "some error"; concurrency tests whose goroutines may all take the fast path; invariant tests asserting rows but not tuples; a table-rebuild migration whose test didn't assert the index came back; composition-root wiring that a wrong constant would silently defeat; assumptions recorded in questions with no test pinning them. Added as bullets under Tests.
- **Task-file loopholes.** Three of five PRs added "added during implementation" Notes to their own task that changed observable behavior (status codes, filters, stricter rules) without a question; one task went done with a criterion moved to another task by a planning PR and nothing in the done file saying so; one PR changed a port another todo task implements and that task's plan was fixed only after the merge. Added: Notes don't settle assumptions, moved criteria leave a dated line, changed ports update the implementing task's criteria (Task state, Dependents); the same rule for workers in `working.md`.

## 2026-10-31: a day-long orchestrated run with three workers, merging everything

Twenty-two tasks merged; the problems were around the loop more than in the reviews. The general ones (commands waiting on stdin, shared scratch dirs mixing two PRs, exit codes read off a notification, secrets handling, unverified coverage claims) went to the general guidelines and `testing.md`; what follows is what changed here:

- **Stale branch base.** Two workers branched from a local `main` without the merged claim: parallel fetches in worktrees of one repo fail on a ref lock, and `sdd start --branch` fell back to the local branch as if there were no remote. The CLI now retries, then fails, and checks the base carries the claim.
- **Repeated flags lost values**, so questions linked one task when the worker typed two. All list flags accumulate now.
- **Frontmatter edited by hand** to add a task to a question or an amendment to an accepted ADR, because no command did it. `sdd link` covers questions and ADRs.
- **A task that needed a real credential and the user's go-ahead** sat in `sdd ready` like any other, and an ordering requirement lived in a sentence instead of `after:`. Added `needs:` and the planning rule.
- **The run never ended**: a parallel answering session kept adding tasks, so "when the ready tasks run out" never fired. The task set is fixed at start now, and "stop" is defined.
- **A built PR waiting on the user had no state.** Findings that changed an accepted decision were resolved by the orchestrator (one wrongly, reverted a round later) or parked as proposed ADRs the user never saw. Added the held outcome, with the question shipped to main so `sdd blockers` shows it, which also meant `validate` had to stop warning about in-progress tasks blocked by a question, and `blockers` had to include them.
- **Rounds weren't defined**, so the model-escalation rule was applied inconsistently and re-reviews were skipped ad hoc; floors made most PRs `high`, rated differently by different reviewers. Defined the round, the one unreviewed fix, and the two-part risk.
- **Reviewers' "read-only" leaked** (refs created in the user's repo, fetches into its checkout) and reviewers skipped the gate because the caches were shared. Fetch into a detached worktree, create nothing; the gate is the implementer's and CI's.
- **The installed tools followed the checkout**: switching this repo to a branch without `sdd` for three minutes broke every worker mid-run. The installer renders pinned copies now and hooks refresh only on the default branch.

## 2026-10-30: an orchestrated run where review rounds cost more than the implementation

Two tasks went through two and three review rounds each. Each round was a fresh reviewer that re-read the whole diff and re-ran the full local check suite, and found a new handful of low findings every time, so the loop kept going on nits. One reviewer, while probing a test, removed the build cache volume every other agent's checks shared, and the next two check runs took minutes instead of seconds. Added: re-reviews get the commit range of the fixes and the decided findings, and review only those (Re-reviews); a round with only low findings ends the loop (`orchestrating.md`); read-only includes shared machine state. Separately, a task that a later decision had invalidated carried the hold only as a Notes line, so `sdd ready` still offered it and a worker was spawned to discover it: holds are blocking questions now (`planning.md`, `answering.md`).

## 2026-11-15: a month of plans where two of three ADRs amended another

One project's records after a month: 197 ADRs, 129 of them amending another, 58 superseded, and 22 still carrying two to ten amendments after seven consolidations. Its 36 business rules had barely changed. About half of the ADRs were written outside planning, by answers to questions and by implementation PRs. What the instructions said at the time, and what went wrong with each:

- **Accepted records were immutable, and an exception "needs an ADR".** Every case a decision's wording didn't foresee became a new record amending it, in planning, in reviews and in answers alike, and nothing asked whether the decision was stated at the wrong level. One chain: a decision that page code reaches the API only through the hooks that report to the agent ("there is no separate hook"), then a record for "the one exception", then a second exception, at which point the user said the rule had only ever been there so the agent could do what the page does, and not to word it as forbidden. That sentence was the decision, and it had never been written down. Added: records are restated in place with the user's agreement, no exceptions are added, and a case is settled from what the record is for (`managing.md`, "How records change"; `planning.md`, "Changing a record").
- **Workers read the Decision without the reason.** `sdd brief` leaves out an ADR's Context to stay short, so a worker had the mechanism and not the purpose, could not tell whether a new case fell under it, and asked. Each answer became a record. Added: the Intent section, printed with the Decision.
- **Planning looked for rules as "what must stay true", stated so a reader can tell whether code keeps them.** That produced closed lists, named files and "never", each falsified by the next feature, and no place for what the user actually wanted ("our calendar and theirs stay in sync"). In another chain an ADR refused a class of operations to agents although a principle said nothing in authorization is agent-specific, and undoing it took a record replacing clauses of four others. Added: business rules as general statements that answer questions, each with the questions it settles, and "Wording a record".
- **A rule with no limit.** The first rule drafted under the new shape said access to a client's data by outsiders is recorded, and doesn't happen when it can't be. The user agreed and added that auditing too much is harmful (storage and database writes): as worded, the rule asked for a write on every read. Added: a rule says what it costs and where it stops, with a question answered "no, that would be too much", and reviews flag a rule applied past what it is for.
- **Consolidation merged the amendments and added nothing.** A record consolidated one day had eight amendments two days later. Added: maintenance restates a record from its intent, with the user.
- **The test for writing an ADR was only in planning.** Answers and implementation PRs recorded details as decisions (the key under which a word is looked up, a log file's size). Added: the same test in `working.md` and `answering.md`, with "no record" as an outcome, and `sdd retire` for the ones already written.
- **Retired records still pile up.** Asked which details to retire, the user added that a record that is outdated and adds nothing should just be deleted. Added: `sdd retire --delete`, with done work keeping the name as history.
- **Everything linked was read whole.** A task that only relied on a component read its whole spec, and nothing showed which docs cost the most across tasks. The user asked that docs be split to minimise what a task reads on average: a backend task reads little of the frontend, a task that uses permissions only their outline. Added: `uses:` links that load a spec's Summary, `sdd cost`, and splitting by who reads a doc.
- **Five briefs dry-run by fresh sub-agents.** Each got one backlog task's brief and the code and planned the work without writing it. About a quarter of each brief was needed. Review checks were 40% of the bytes and 7% of their bullets applied, since a task got every check in every area of every record it linked. And each task had a design choice nobody had made (a response type four operations return where the task named two, an alert text the alert model can't produce). Added: a task's brief carries only the checks of what it links, checks a test can hold become acceptance criteria, and planning dry-runs its tasks before shipping.
- **Specs and records restated the code.** Specs narrated job names, conditions and error codes, records listed lint rules and file allowlists, and both needed corrections as the code moved. Added: the level set in `overview.md`, feature specs deleted when their feature is built, and no review check for what a test enforces.

## 2026-11-15: an orchestrated run where what followed each PR cost more than building it

Thirteen PRs with three tasks in flight, in a project with no CI whose checks had to pass locally on the PR merged into current main. By the run's own analysis, most of its tokens and agent time went to what happened after each PR was first opened. One cause changed `orchestrating.md`; the other was the project's and went to its own instructions:

- **Fix rounds resumed the worker that built the PR.** The instructions allowed a new worker but named the resumed one first. By the first review that worker's session held everything it had read to build the PR, and every turn of a fix re-read it, a one-line doc fix included. Changed: a fix round is a new worker, started once the previous one has reported.
- **Every merge sent every other open PR back to its worker.** With three PRs open and the project's rule that checks pass on the merged result, each merge to main made the other workers merge main and run the checks again, several times per PR, and main moved again while they did. Not changed here: with CI the checks run on the PR by themselves and a merge only concerns the PRs it conflicts with, which is all `orchestrating.md` covers. A project without CI says in its own instructions when main is brought in and who runs the checks.

## 2026-11-18: an orchestrated run where no PR passed its first review

Twenty PRs, none approved in round 1. In seven, the first review's findings were what the reviewer read and the worker didn't, and the last fixes after the reviews cost more than they changed:

- **Area checks only the reviewer ran.** Workers got the checks of what their task linked; reviewers added those of the areas the diff touched. Two PRs changed what the assistant shows without linking the rule that requires real-model evals for it, and one ran a migration without the deploy ADR's timing check. Each cost a fix round, and two of them a re-review too. Changed: the worker runs `sdd checks --area` on its diff before its checks, links what was missing and says so; the reviewer still picks the areas itself and reports the missing link as a planning finding.
- **Dependents only the reviewer read.** Only the review brief carried the dependent tasks, whole, so three PRs were flagged on what their dependents would need, and most review briefs were too long to print. Changed: both briefs carry each dependent's Goal and criteria, without its Notes, and the worker is told to leave room for them, not to build them.
- **Final low fixes on new workers.** Thirteen workers were started only for a round's last lows, some to edit four lines of prose or to record a tech-debt task, and each first loaded the docs, the brief and the PR. Changed: that fix goes to the worker that made the last commit, by message, where the tool can resume it. Their check runs went to the project: `sdd changes` tells a range that changed only docs from code, for its instructions to say what each needs.
