# redact-secrets

Replaces secret values in tool results with `[REDACTED:NAME]` before the model reads them, so a `cat .env`, a `printenv` or a stray `secrets get` doesn't put a secret in what the model reads. Each redacted result ends with a note telling the model not to print secrets, to use `secrets has NAME` / `secrets list` instead, and not to write redacted text back into a file.

It hooks `session.append` for tool results and for the rows the engine attaches beside them (a changed file, a hook's context), so it covers every tool (Bash, Read, Grep, MCP...) and subagents too. It also hooks the prompts and deliveries that don't come from the person: a background task's or a Monitor's notification, another session's message and an SDK host's turn (`claude -p`, the Agent SDK: a program, not the person) (doors `prompt` and `delivery`), and the notes other plugins append for the model (door `note`; this plugin appends none, and a plugin's own append never runs its own hook, so nothing loops). Only what the engine attests as the person (origins `composer`, their Enter at the terminal; `bridge`, Remote Control; `slack-ping`, the session's owner from Slack) reaches the model as sent, and so does the output of a command the person ran themselves (door `command`): a secret in those is one they chose to share.

An attachment the engine renders for each request keeps its row as made whatever a `session.append` hook answers, and the plugin API doesn't say which kinds those are, so the plugin also redacts every attachment at `prompt.attachment`, as a request carries it. Except `queued_command`, a prompt or notification delivered into a running turn: there its sender can't be told apart, so it is redacted only at `session.append`, where it can; if the engine renders it per request, a notification delivered into a running turn reaches the model unredacted. The matching is done by `secrets redact` from the `secrets` CLI (`features/core/bin/secrets`, on `PATH` through `install.sh`): the text goes to its stdin and comes back redacted, so the values stay in that process and the plugin never holds them. What it can't change is the transcript file: Claude Code keeps each tool's raw output there (`toolUseResult`) next to the redacted message, so don't share a transcript as if it were clean.

What counts as a secret is best effort, decided by `secrets redact` from the variable's name: a value is redacted when the name has `SECRET`, `TOKEN`, `PASSWORD`, `PASSWD`, `PASSPHRASE`, `CREDENTIAL` or `APIKEY` in it, or `KEY` or `PASS` as a whole `_`-separated word (so `API_KEY` and `AWS_KEY_ID` match, `MONKEY` and `KEYBOARD_LAYOUT` don't), unless it also looks like config (`*_PATH`, `*_FILE`, `*_DIR`, `*_TTL`, `*_LENGTH`, `*_PREFIX`, and `GOOGLE_APPLICATION_CREDENTIALS`, a path by convention).

- **Where values come from:** the environment Claude Code runs with (a variable exported only inside the Bash tool's shell isn't in it), the env files of the working directory and of its parents up to the git root (`.env`, `.env.*` except placeholders like `.env.example`, `.secrets`; not a direnv `.envrc`, whose values are often shell expressions: add it to `files.include` if yours are plain), and any files listed in `$SECRETS_REDACT_FILES` (`:`-separated). Subdirectories aren't searched; add a pattern like `apps/*/.env` to `files.include` for those.
- **How a value is matched:** as parsed, as written in the file (a double-quoted value with `\n` escapes shows them in `cat .env`), and, when it spans lines, by the parts of each line that look like key material (a numbered listing of the file or a `grep` splits it): a line of 16+ characters with no spaces, or, in a line with spaces, each word of 32+ characters (a multi-line JSON credential's `"private_key": "..."` and `"private_key_id": "..."`). `-----BEGIN`/`-----END` lines, URLs, email addresses and short words (the same credential's `"type": "service_account",`) are ordinary text elsewhere and are left alone. Commented-out assignments (`# API_KEY=...`, `#export API_KEY=...`) and the earlier assignments of a name that appears twice are redacted too, though `secrets list`/`has`/`get` see neither. A commented-out assignment is read from its own line only, so of a commented-out multi-line value only the first line is redacted (none of a commented-out PEM block: its first line is the `-----BEGIN` marker every key has), and it is skipped when its value is clearly a placeholder: `<...>`, `your-...` or `your_...` (any case), a run of `x`, `*`, `.` or `-` only (`xxxx`, `***`, `...`), or `changeme`. A value in an env file that is only a reference to another variable is skipped: `${NAME}`, or `$NAME` with a name in env-var style (capitals, digits and `_`). That is a guess from the shape: a literal password written that way (`$ABC123`) is skipped too, while `$ecretPassw0rd` is a value. `$SECRETS_CONFIG` and `$SECRETS_REDACT_FILES`, the CLI's own settings, are never secrets.
- **Short and plain values:** values under 6 characters are left alone, so something like `TOKEN_LENGTH=8` can't replace every `8` in the output. Letters-only or digits-only values under 16 characters (`postgres`, `123456`) are only redacted right after their variable name (`POSTGRES_PASSWORD=...`), since they're ordinary words elsewhere (`image: postgres:16`).
- **URL passwords:** the password of any `scheme://user:password@host` URL is masked wherever it appears (`postgres://app:[REDACTED:url-password]@db/main`), whatever variable it came from; the rest of the URL stays readable. A JSON-escaped URL (`https:\/\/u:pw@h\/x`) is masked too. A `/` in the password has to be percent-encoded, as for any URL a client can use, and so does an `@` in the user: `https://me@corp.com:pw@git.host/repo` isn't masked.
- **Bounds:** to stay within the plugin's timeout, `secrets redact` reads at most 50 env files and 4 MiB of them in all, skipping a file over 1 MiB and the files past that budget, and looks for at most 10,000 distinct values, the first found: the environment's, then those of `$SECRETS_REDACT_FILES`, then those of the env files of the directories. A repository that commits files built to exhaust them (thousands of junk values in a `.env.*`, files over 1 MiB, a few very repetitive values against a megabyte of output) can still make redaction skip the user's own `.env.*` files or run past the timeout, and the result is then stored unredacted with a toast. That is not defended against beyond these bounds: the goal is stopping an agent from reading a secret by accident, not a hostile repository.
- **Settings:** the name patterns, the exclusions, the minimum length and the file patterns are settings of the CLI, in `~/.config/secrets-cli/config.json` or the file `$SECRETS_CONFIG` names; `secrets --help` has the format and the defaults.

Out of scope on purpose: values of other names (a webhook URL, say, unless you add `*WEBHOOK*` to the names), encoded or split values, and anything the model derives from a secret. A `Read` of `.env` shows the secret lines redacted, so the plugin refuses a `Write` or `Edit` that would put a `[REDACTED:` marker into an env file; editing the secret lines themselves has to happen outside the session. That guard covers only the `Write` and `Edit` tools and only files named `.env`, `.env.*` or `.secrets`: a Bash redirect (`cat > .env`, `tee`, `sed -i`) and a file matched only by a custom `files.include` or listed in `$SECRETS_REDACT_FILES` aren't guarded.

If `secrets redact` can't run (the CLI isn't on `PATH`, e.g. `install.sh` hasn't run, or it times out or the output is too large to redact), the result is stored unredacted and a toast says so once per distinct reason: failing closed would make every tool unusable.

Install: `ai-workflow/install.sh`, like the other plugins of the repo. Develop: `claude plugin validate .` and `claude plugin test .`; the CLI itself is tested with pytest (`features/core/tests/test_secrets.py`).
